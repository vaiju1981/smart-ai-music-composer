# Parser Benchmark Corpus

This document defines how the Phase 1 prompt-parser benchmark corpus is created, reviewed, frozen, and scored. The corpus lives at `tests/fixtures/parser_benchmark.jsonl` and contains exactly 100 records.

## Record schema

Each JSON Lines record contains:

- `id`: stable unique identifier.
- `category`: `supported_paraphrase | boundary | malformed | unsupported`.
- `prompt`: exact user input.
- `expected_outcome`: `accepted | rejected`.
- `expected_spec`: complete canonical `CompositionSpec` when accepted; otherwise `null`.
- `expected_error`: stable error code when rejected; otherwise `null`.
- `label_rationale`: short explanation of the expected result.

## Composition and labeling

The corpus is generated by `scripts/generate_parser_corpus.py` and committed to the repository. To extend or revise:

1. Edit the generator functions in `scripts/generate_parser_corpus.py`.
2. Run `python scripts/generate_parser_corpus.py` — the script asserts the corpus is exactly 100 records.
3. Re-label any record whose label changed. The script's `label_rationale` strings serve as the primary labeler pass.
4. Pre-adjudication field-level agreement is currently SKIPPED in Phase 1 (per operator direction during scaffolding); every label here is a single labeler's call. The 90% gate described above is a release-gate to reinstate before Phase 2 model selection (per §10 #3).

The corpus must cover all three Phase 1 moods, duration boundaries, optional/default fields, spelling and phrasing variation, conflicting instructions, malformed durations, famous-piece requests, unsupported instruments, and unsupported musical traditions.

The primary labeler assigns every expected field using the frozen `CompositionSpec` and product rules. Labels are calibrated for an LLM-quality parser that follows the §6 retry policy; the deterministic fallback parser is documented as failing a small set of tie-break records (two mood keywords present, compound durations) where the LLM is expected to do better. This is expected behavior, not a corpus defect.

## Freeze and versioning

- Freeze the labeling guide before scoring candidate models.
- Commit the corpus and record its SHA-256 in `MODELS.md` with every benchmark run.
- Changing a prompt or expected label creates a new corpus version and invalidates comparisons with results from the previous version.
- Keep the final model-selection corpus out of model prompts, training, and repair examples.

## Scoring

Use the thresholds in §8 of [`roadmap.md`](roadmap.md). Report first-response schema validity, post-repair/fallback success, field-level semantic exact match, unsupported-request rejection, p50/p95 latency, and total benchmark cost.
